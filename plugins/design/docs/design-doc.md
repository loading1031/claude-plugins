# 로컬 디자인 문서

와이어프레임과 승인된 화면 설명은 프로젝트 루트 `design/`에 둔다. 토큰·컴포넌트는 프로젝트 코드를 원본으로 삼고, 실제 원본을 참조하는 카탈로그에 전시한다. 이 플러그인은 설계와 구현을 연결하는 공통 규약을 정하며 UI 기술과 전시 도구는 프로젝트가 선택한다.

## 선언과 산출물

`/design:init`이 프로젝트 `CLAUDE.md`에 기록한다.

```markdown
## 디자인
- 문서: design/index.html
- 기준: 없음
- 토큰 원본: <확인한 코드 경로 또는 미정>
- 컴포넌트 원본: <확인한 코드 경로 또는 미정>
- 카탈로그: <진입 경로와 실행 방법 또는 미정>
```

- `design/index.html`을 로컬 미리보기의 진입점으로 둔다. 사용자가 지정한 다른 프로젝트 내부 경로가 있으면 따른다.
- 문서의 탐색 UI·CSS·스크립트·SVG와 수정 원본은 프로젝트에서 재현 가능하게 둔다. 단일 HTML, 여러 페이지, 기존 프로젝트 빌드 중 필요한 만큼 사용하며 새 프레임워크나 서버를 필수로 도입하지 않는다.
- 설계 문서는 바로 여는 HTML을 기본으로 한다. 실제 컴포넌트 카탈로그는 프로젝트의 기존 서버나 빌드를 사용할 수 있으며 실행 방법과 원본 위치를 안내한다. 기존 UI 프레임워크·테마·컴포넌트를 사용하고, 외부 CDN·별도 계정에 미리보기를 의존시키지 않는다.
- 에이전트가 파일을 직접 생성·연결한다. Claude 아티팩트나 Claude Docs 로그인·커넥터·토큰, 사용자 수동 업로드는 이 흐름의 선행 조건이 아니다.
- 기존 외부 디자인은 참고 자료로 읽을 수 있다. 필수 참고 자료를 읽지 못하면 사용자에게 접근 가능한 링크나 파일을 요청한다. 기존 외부 문서와 프로젝트 자료를 임의로 삭제하지 않는다.

## 설계 순서와 탐색 구조

1. 기존 UI 기술·카탈로그·테마와 토큰·공유 컴포넌트를 찾는다.
2. 전체 IA(정보 구조), 사용자 흐름, 화면 설명과 와이어프레임을 작성하고 승인 기준을 확인한다.
3. 승인된 구조에 필요한 토큰·컴포넌트를 기존 코드에 구현하거나 보완한다.
4. 같은 원본을 카탈로그에 연결해 옵션·상태·사용법을 전시한다.
5. 화면 구현이 요청되면 컴포넌트를 조합하고 반응형·상호작용을 검증한다.

전체 작업의 순서이며, 사용자가 요청한 단계만 수행한다. 컴포넌트 작업만 요청받았을 때 전체 화면이나 서버 저장·권한 기능까지 만들지 않는다. 화면은 컴포넌트의 조합 예시로 제공할 수 있으며 예시 범위를 명시한다.

```text
화면                  ← 개요: 전체 IA, 사용자 흐름, 화면 목록
├ 대시보드            ← 목적·설명 + 와이어프레임
├ 종목 차트
└ 컴포넌트·토큰       ← 실제 카탈로그와 코드 원본으로 연결
   ├ 버튼             ← 옵션·상태·사용법 전시 링크
   ├ 차트 카드
   └ 토큰             ← 코드에서 읽은 색·간격·글꼴·둥글기
```

- 왼쪽 사이드바에 화면별 페이지 이름을 표시한다. 선택하면 해당 화면의 설명과 와이어프레임이 열린다. 좁은 화면에서는 접거나 상단 메뉴로 바꿀 수 있다. 문서 탐색 메뉴와 제품의 실제 메뉴를 구분한다.
- 화면 설명에는 목적, 진입·복귀 경로, 주요 행동, 로딩·빈 값·오류·권한 등 관련 상태, 확정 규칙과 미정 사항을 적는다. 개요의 흐름과 화면 사이 이동이 일치해야 한다.
- 그림은 실제 SVG 도형·텍스트 또는 HTML/CSS로 작성한다. PNG를 감싼 SVG는 벡터 와이어프레임으로 취급하지 않는다. 사진·렌더 이미지에는 비트맵을 사용할 수 있다. SVG 구조안과 실제 UI 프레임워크로 렌더한 시안은 구분해 설명한다.
- 도형·텍스트를 지나치게 축소하지 않는다. 필요하면 흐름을 여러 그림으로 나누거나 확대·가로 스크롤을 제공한다.
- 컴포넌트·토큰 항목은 실제 카탈로그의 해당 전시와 원본 위치로 연결한다. 기존 카탈로그가 있으면 `design/`에 전시 화면이나 CSS·토큰 복사본을 추가하지 않는다.

## 프로젝트별 카탈로그 연결

패턴 라이브러리는 컴포넌트를 모아 보여주는 방식이며 특정 패키지 이름을 뜻하지 않는다. 기존 전시 도구를 우선 사용하고, 없으면 기존 렌더러로 가벼운 카탈로그를 만들 수 있다. HTML 카탈로그도 공유 원본에서 생성되면 이 규약을 따른다.

| 프로젝트 UI | 연결 예시 |
|---|---|
| Django 템플릿 | 기존 Django 패턴 라이브러리 또는 개발용 카탈로그에서 실제 include를 렌더한다 |
| Kotlin·Spring과 Thymeleaf 등 서버 템플릿 | 프로젝트의 실제 템플릿 조각을 개발용 카탈로그에서 렌더한다 |
| React·Vue·Web Components 등 | 기존 Storybook 등 해당 UI 기술에 맞는 전시 도구에서 실제 컴포넌트를 불러온다 |

예시는 도구 선택을 강제하지 않는다. 백엔드 언어만으로 전시 도구를 결정하지 않으며, 카탈로그를 위해 별도 Django 서버나 새 프런트엔드 프레임워크를 공통 의존성으로 도입하지 않는다.

- 토큰은 프로젝트 테마·CSS 변수·토큰 파일을 원본으로 한다. 색상 견본과 수치 전시는 원본에서 읽거나 생성한다. 토큰을 만들기 전 임의 값을 확정하지 않는다.
- 컴포넌트는 실제 코드·템플릿을 import/include해 전시한다. 기본·오류·로딩 상태를 전시하려고 같은 마크업을 다시 작성하지 않는다. 토큰과 CSS도 제품과 같은 원본에서 가져오며, 정적 내보내기는 생성물임을 표시하고 재생성 방법을 둔다.
- 각 컴포넌트에 실물, 입력값·옵션, 사용 예시, 코드 원본 위치를 제공한다. 관련된 로딩·빈 값·오류·권한·선택·비활성·저장 전/중/성공/실패 상태와 좁은 화면의 배치를 전시한다. 모든 상태를 모든 컴포넌트에 기계적으로 추가하지 않는다.
- 여러 화면에 반복되는 도메인 UI를 공유 컴포넌트로 만든다. 단일 화면의 배치를 전부 새 컴포넌트로 추출할 필요는 없다.
- 화면 시안과 카탈로그가 같은 컴포넌트·테마 원본을 참조하도록 연결한다. 예시 데이터와 모의 동작을 실제 API·DB 저장·권한 검사와 구분한다. 카탈로그의 예시가 실제 제품의 권한·저장 기능을 대신하지 않는다.

## 무엇이 기준인가

| 자료 | 기준 | 흐름 |
|---|---|---|
| 토큰 | 프로젝트 코드의 테마·토큰 파일 | 카탈로그는 원본에서 값과 견본을 읽는다. 코드가 없으면 미정으로 둔다 |
| 컴포넌트 | 프로젝트 UI 컴포넌트 코드 | 카탈로그는 같은 원본의 옵션·상태·사용법을 전시하고 설계 문서가 연결한다 |
| 화면 | 승인된 로컬 디자인 문서 | IA·흐름·와이어프레임을 먼저 정하고 구현이 승인 기준을 따른다 |

## 기준과 변경 이력

- 문서·SVG·소스를 Git으로 함께 관리한다. 자동으로 증가하는 Claude Docs의 탭 rev·그림 pub은 사용하지 않는다.
- 사용자가 승인한 디자인은 실제 Git 커밋/태그와 관련 파일 경로로 식별한다. Git을 사용하지 않으면 승인된 스냅샷 경로를 기록한다. 승인 전에는 `기준: 없음`을 유지하며 커밋·태그·스냅샷을 임의로 만들어 승인되었다고 표시하지 않는다.
- 화면 구현 전에 선언된 기준에서 화면과 참조 컴포넌트를 읽는다. 현재 문서와 승인 기준이 다르면 관련 차이를 확인하고, 지시가 명확하지 않은 경우 사용자에게 기준을 묻는다.
- 구현 커밋을 작성할 때 반영한 문서와 승인 기준을 기록한다. 예: `디자인: design/index.html#dashboard, 기준 <승인 커밋>`.
- 디자인 수정 시 관련 화면·공유 컴포넌트·문서의 연결을 함께 갱신한다. 새 기준은 사용자 승인 후 기록한다. 이 플러그인이 커밋·공개 게시를 별도로 승인하는 것은 아니다.

## 디자인 작성 후 검토

디자인 작성이 끝나면 변경한 HTML·JSON·SVG 파일을 포함한 PR에서 검토한다. 문제는 해당 파일의 관련 줄에 연결한 PR 리뷰 의견으로 남겨 변경과 함께 검토·수정 이력을 관리한다. 각 의견에는 심각도, 화면 코드, 근거, 사용자 영향, 최소 수정안을 포함한다.

디자인 검토만을 위한 별도 `review.html`을 만들거나 리뷰 의견을 설계서 HTML에 삽입하지 않는다. PR이 아직 없으면 검토 가능한 PR을 준비한다. 사용 가능한 PR 리뷰 기능이 없는 환경에서는 이를 명시하고, 대체 게시 위치는 사용자와 정한다. PR 리뷰는 설계 초안을 승인 기준으로 자동 승격하지 않는다. 디자인 기준은 기존 승인 절차에 따라 별도로 기록한다.

## 미리보기와 확인

가능한 로컬 미리보기에서 IA·화면 탐색과 SVG 가독성을 확인한다. 카탈로그에서는 토큰과 컴포넌트의 상태·옵션을, 조합한 화면에서는 반응형과 실제 사용자 흐름을 확인하고 각각의 결과를 기록한다. 도구가 미리보기를 지원하지 않으면 그 한계를 보고하고, 파일 생성·빌드 성공을 시각 검증으로 표시하지 않는다. 결과에는 설계 문서·카탈로그의 실제 진입 경로와 확인 범위를 포함한다.
