# 로컬 디자인 문서

근거: `${CLAUDE_SKILL_DIR}/../../docs/design-doc.md`. 디자인은 프로젝트 루트 `design/`의 HTML·SVG와 수정 가능한 원본으로 관리한다. Claude 아티팩트나 Claude Docs 도구를 전제로 하지 않는다.

프로젝트 `CLAUDE.md`의 "## 디자인" 절(로컬 문서 경로, 승인 기준, 카탈로그와 코드 원본)을 따른다. 절이 없으면 기존 `design/`와 컴포넌트 카탈로그를 확인하고 `/design:init` 절차로 연결한다.

- 기존 UI 기술·테마·토큰 원본·공유 컴포넌트·전시 도구를 먼저 확인한다. 전체 작업은 기존 자산 확인 → IA·와이어프레임 제작·승인 → 필요한 토큰·컴포넌트 구현 → 카탈로그에 옵션·상태·사용법 전시 → 화면 조합·검증 순서로 진행한다. 사용자가 요청한 단계만 수행하며 컴포넌트 작업을 전체 화면·백엔드 구현으로 확장하지 않는다.

- 화면 구현 전에 승인 기준의 화면 설명·와이어프레임과 참조 컴포넌트를 읽는다. 승인 기준과 현재 문서가 다르고 어느 쪽을 따를지 명확하지 않으면 사용자에게 확인한다. 승인 전 초안을 확정된 기준으로 표시하지 않는다.
- 문서 구성은 전체 IA·사용자 흐름 → 왼쪽 화면별 페이지 → 각 화면의 설명·와이어프레임 순서를 따른다. 컴포넌트·토큰 항목은 실제 카탈로그의 해당 예시와 코드 원본으로 연결한다. 기존 카탈로그의 전시 페이지를 `design/`에 다시 만들지 않는다.
- 와이어프레임은 실제 SVG 또는 HTML/CSS로 만든다. PNG를 SVG 안에 넣어 벡터처럼 표시하지 않는다. 사진·렌더 이미지 등 비트맵 에셋은 필요에 따라 쓴다. 문서 폭 때문에 글자가 읽기 어려워지면 그림 분할·확대·영역 스크롤을 제공한다.
- 토큰·컴포넌트 원본은 프로젝트 코드에 두고 전시 도구가 그 원본을 참조한다. 기존 Storybook, Django 패턴 라이브러리, 서버 템플릿 카탈로그 등이 있으면 확장한다. 도구는 실제 프런트엔드 기술에 맞추며 특정 언어·프레임워크·전시 패키지를 공통 필수 의존성으로 만들지 않는다. 전시 도구가 없으면 프로젝트의 기존 렌더러로 가벼운 카탈로그를 구성할 수 있다.
- 컴포넌트별 실물·입력값과 옵션·관련 상태·사용 예시·원본 위치를 전시한다. 전시와 화면 시안은 같은 컴포넌트 및 테마 원본을 사용하고, 상태 예시를 만들기 위해 마크업이나 토큰 값을 따로 복제하지 않는다. 정적 HTML 카탈로그라면 공통 원본에서 생성하고 재생성 방법을 기록한다. 토큰 원본이 없으면 미정으로 표시한다.
- 화면 시안은 승인된 흐름에 따른 조합 예시로 둔다. 예시 데이터·모의 저장과 실제 서버 동작을 구분하며, 카탈로그의 상태 확인과 실제 화면의 반응형·상호작용 검증을 각각 기록한다.
- 로컬 파일을 직접 수정하고 상대경로·자산 연결을 유지한다. 사용자가 파일을 하나씩 업로드하도록 요구하지 않는다. 참고 외부 문서가 필수인데 읽을 수 없으면 자료 접근을 요청한다.
- 문서와 SVG 변경은 Git으로 함께 추적한다. 구현 커밋을 만들 때 반영한 문서 경로와 승인 기준 커밋/태그를 기록한다. 사용자가 디자인을 확정하면 "기준"을 실제 승인 버전으로 갱신한다. 별도 rev·pub 번호를 만들어 운영하지 않는다.
- 가능한 미리보기에서 렌더링·화면 탐색을 확인하고 확인한 범위를 보고한다. 빌드 성공과 시각 검증을 구분한다.
- 디자인 작성 후 검토는 변경 파일을 포함한 PR에서 진행하고, 발견한 문제는 해당 HTML·JSON·SVG 줄에 연결된 PR 리뷰 의견으로 남긴다. 의견에는 심각도, 화면 코드, 근거, 사용자 영향, 최소 수정안을 포함한다.
- 디자인 검토만을 위한 별도 리뷰 HTML을 만들거나 리뷰 의견을 제품 설계 HTML에 삽입하지 않는다. 아직 PR이 없으면 변경을 PR로 검토할 수 있게 준비하고, PR 리뷰 기능을 사용할 수 없는 환경에서는 제한을 알린 뒤 대체 위치를 사용자와 정한다.
