# /planning:backlog — 다음 기획 주제 고르기

먼저 `rules` 스킬을 따른다(프로젝트 기획 설정 읽기, backlog 형식). 인자: `$ARGUMENTS`

## 인자 없음 — 다음 주제 추천
1. `<폴더>/backlog.md`를 읽는다. "권장 순서" 표가 있으면 그 순서를 우선한다.
2. "진행 중" 항목이 있으면 브랜치와 함께 먼저 알린다. 현재 브랜치가 그중 하나면 그 항목을 이어서 하자고 제안한다.
3. 후보를 P0 → P1 → P2 순으로 보여 주고, 다음 주제 하나를 이유와 함께 추천한다.
   추천 기준: 다음 마일스톤 착수를 막는가(P0) → 다른 항목의 선행인가 → 결정만 하면 되는가(조사가 적은가) → 선행 조건(사용자 준비물)이 갖춰졌는가
4. "동기화 빚"이 있으면 함께 알린다.

## add <주제>
1. 겹치는 후보가 있는지 확인하고, 있으면 합칠지 묻는다.
2. 다음 ID로 "후보" 표에 추가한다. 왜 필요한지, 선행, 우선순위를 사용자와 정한다.
3. 지금 논의 중인 주제가 있으면 그 주제로 돌아간다. **새 후보를 바로 파고들지 않는다.**

## pick <ID>
1. 브랜치를 준비한다 (`rules` 1.5):
   - `git status --short`가 비어 있지 않으면 멈추고 어떻게 할지 묻는다.
   - 기본 브랜치로 전환해 최신인지 확인하고, `plan/<ID>-<slug>`를 만들어 전환한다. 이미 있으면 그 브랜치로 전환한다. 기본 브랜치가 다른 worktree에 열려 있으면 `git fetch` 뒤 `git switch -c plan/<ID>-<slug> origin/<기본>`으로 만든다(`rules` 1.5).
   - 원격이 GitHub이고 항목에 이슈가 있으면 이슈 번호를 확인해 둔다(커밋 `Refs:`와 PR `Closes`에 쓴다).
   - 작업지시서가 `issue`인데 이슈가 없으면 `rules` 1.6 템플릿으로 이슈를 만든다. 제목과 본문을 먼저 보여 주고 확인받는다.
   - git 저장소가 아니면 브랜치 없이 진행할지 묻는다.
   - **항목이 기본 브랜치의 backlog.md에 없으면** 다른 브랜치에서 추가된 것일 수 있다. `git log --all --oneline -S "| <ID> |" -- <폴더>/backlog.md`로 찾아, 그 브랜치가 아직 안 합쳐졌으면 사용자에게 알리고 (a) 그 브랜치를 먼저 합친다 (b) 기본 브랜치에서 시작하고 행을 다시 적는다 중에서 고르게 한다.
2. 항목을 "진행 중"으로 옮기고 브랜치 이름, 이슈 번호(있으면), 날짜를 적는다. 후보 행이 길면(`rules` 2) 상세를 이슈 본문으로 옮기고 행을 줄인다.
3. 작업지시서를 먼저 읽는다(진행 메모 포함). `issue`: `gh issue view <N> --comments`, `file`: `work-orders.md`의 해당 절. 그다음 관련 문서 절을 읽고 **이미 정해진 것**과 **열린 질문**을 정리해 보여 준다. 사용자 준비물이 안 갖춰졌으면 먼저 알린다.
4. 조사가 필요하면 출처를 열어 확인한다. 열린 질문은 한 번에 1~3개씩 묻는다.
5. 결정이 모이면 `/planning:spec <주제>`를 제안한다.

## sweep
1. 기준 문서와 주제 문서의 "확인이 필요한 것", "제안", "검증하지 않음" 표시와 이번 대화에서 나온 주제를 훑는다.
2. 기존 후보와 겹치지 않는 것만 후보로 제안하고, 사용자가 고른 것만 추가한다.

## 규칙
- 세션 하나에서 백로그 항목 1~2개만 다룬다. 대화가 길어지면 결정된 것만 `/planning:spec`으로 반영하고 나머지는 백로그에 남기자고 제안한다.
- 백로그만 바뀌었으면 log.md에는 쓰지 않는다. 커밋은 `/planning:commit`(`docs: 백로그 갱신`).
