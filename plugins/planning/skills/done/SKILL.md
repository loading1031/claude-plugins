# /planning:done — 기획 브랜치 마무리

먼저 `rules` 스킬을 따른다(기획 설정, 1.5 브랜치). 인자: `$ARGUMENTS` (없으면 현재 브랜치의 항목)


먼저 `rules`에서 백로그 모드를 확인한다. **이슈 모드이면 [이슈 모드 참조](../rules/references/issue-backlog.md)의 이 명령 절차를 적용하고 아래 파일 모드 절차는 실행하지 않는다.** 프로젝트의 명시적 예외와 기존 사용자 승인 범위를 우선한다.

## 절차

1. **대상 확인**: 인자 ID 또는 현재 브랜치로 `backlog.md` "진행 중" 항목을 찾는다. 기본 브랜치에 있고 인자도 없으면 진행 중 목록을 보여 주고 묻는다.
2. **남은 것 확인**: 커밋되지 않은 변경이 있으면 멈추고 `/planning:commit`을 먼저 하자고 한다. 이 브랜치에서 결정했지만 문서에 안 쓴 것이 있는지, 열린 질문이 백로그 후보로 옮겨졌는지 확인한다.
3. **실행 이관 확인**:
   - **이슈 모드:** 스펙에 실행 가능한 사용자 흐름이 있으면 디자인·개발 후속 작업을 기존 이슈에 연결하거나 새 이슈로 만든다. 기존 이슈는 범위와 완료 기준을 확인해 재사용하고, 새 이슈에는 목표·범위·스펙 링크·선행 조건·사용자 관점 완료 기준·검증 방법을 적는다. 디자인은 별도 산출물이 필요한 경우에만 분리하며, 디자인이 구현을 막지 않으면 개발과 병행 가능하게 한다. 구현을 막지 않는 미정 사항은 제안/후속 구현 범위로 둔다. 후속 이슈 번호와 의존 순서를 기획 이슈에 기록한다.
   - **파일 모드:** 실행할 작업이 남으면 `backlog.md` 후보와 `work-orders.md` 지시서로 다음 디자인·개발 작업을 추적한다. 구현을 막지 않는 미정 사항은 기획 완료를 막지 않는다.
   - 후속 작업 연결 또는 추적이 끝나지 않았거나 구현을 막는 결정이 남아 있으면 기획 이슈를 닫는 PR을 만들지 않는다. 미완료 사유와 다음 행동을 기록한다.
4. **백로그 완료 처리** (기획 브랜치에서): 항목을 "완료"로 옮기고 결과 문서와 날짜를 적는다. 작업지시서가 `file`이고 `work-orders.md`에 이 항목의 절이 있으면 지운다(`issue`면 PR의 `Closes`로 닫힌다). `docs: <ID> 완료 처리`로 커밋한다.
5. **합치기 미리보기**: 원격이 있으면 먼저 `git fetch`. `git log --oneline <기본>..<브랜치>`와 `git diff --stat <기본>...<브랜치>`를 보여 준다. 기본 브랜치가 그사이 앞서갔으면 알린다. 합치기 방식(기획 설정 "합치기 방식")과 닫을 이슈를 함께 보여 준다.
6. **사용자 확인 후 합치기** — 머지 커밋을 남기는 방식만 쓴다(squash·rebase 안 함).
   - **PR 방식** (원격이 GitHub이고 `gh`를 쓸 수 있을 때. 기본):
     ```bash
     git push -u origin <브랜치>
     gh pr create --base <기본> --head <브랜치> --title "docs: <ID> <주제> 기획" --label plan --body "<결과 요약>

     Closes #<이슈>"
     gh pr merge <PR 번호> --merge --subject "docs: <ID> <주제> 기획" --body "Closes #<이슈>"
     ```
     항목에 이슈가 없으면 `Closes` 줄을 뺀다. 대상 저장소에 `plan` 라벨이 있는지 먼저 확인하고 없으면 생성한다. PR 주소와 적용 라벨을 보여 준다.
   - **로컬 방식** (원격이 없을 때):
     ```bash
     git switch <기본 브랜치>
     git merge --no-ff <브랜치> -m "docs: <ID> <주제> 기획"
     ```
   - **worktree:** 기본 브랜치가 다른 worktree에 체크아웃돼 있으면(`git worktree list`) 이 폴더에서 `git switch`할 수 없다. 로컬 방식이면 그 폴더에서 `git -C <폴더> merge …`로 합친다.
   - `backlog.md`, `log.md` 충돌은 양쪽 항목을 모두 살려 푼다(log는 날짜순, backlog는 ID순). 그 외 충돌은 내용을 보여 주고 사용자에게 묻는다.
7. **정리**:
   - 기본 브랜치가 체크아웃된 폴더에서 `git pull --ff-only`로 원격에 맞춘다(PR 방식).
   - 합쳐진 것을 확인한 뒤 로컬 브랜치를 지운다(`git branch -d`). 지금 폴더가 그 브랜치에 있으면 먼저 `git switch --detach origin/<기본>`(worktree) 또는 `git switch <기본>`.
   - 원격 브랜치는 지우지 않고, 지울지 묻지도 않는다(`rules` 1.5). 사용자가 직접 지운다.
   - 이슈 본문·댓글에 브랜치 경로(`blob/<브랜치>/…`) 링크가 있으면 기본 브랜치 경로로 바꾼다.
8. **요약**: 합쳐진 커밋(머지 커밋, PR 번호), 닫힌 기획 이슈, 생성하거나 재사용한 디자인·개발 이슈, 의존 순서, 다음 실행 작업을 짧게 보여 준다.

## 규칙
- 합치기(PR 생성·머지 포함)는 사용자 확인 후에만 한다. 합친 뒤 로컬 브랜치 삭제는 확인 없이 한다. 원격 브랜치는 지우지 않는다.
- push는 이 절차의 PR 방식에서 사용자가 합치기를 확인했을 때, 또는 사용자가 요청할 때만 한다.
- `--force`, `reset --hard`를 쓰지 않는다.
