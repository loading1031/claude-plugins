# /planning:handoff — 다음 세션을 위한 작업지시서

먼저 `rules` 스킬을 따른다(1.6 작업지시서 형식과 둘 곳: 기획 설정 "작업지시서" `issue` | `file`). 인자: `$ARGUMENTS` (특정 ID만 쓰려면 지정, 없으면 아래 기준으로 고름)

## 절차

1. **대상 고르기**
   - 현재 진행 중인 항목(브랜치가 열려 있는 것): 진행 메모를 갱신한다.
   - 다음에 할 후보: `backlog.md`의 P0 전부와, 사용자가 지목한 항목. 이미 지시서가 있으면 이번 세션에서 바뀐 것만 고친다.
2. **진행 중 항목의 진행 메모** — 이번 대화에서:
   - 결정된 것 중 아직 문서에 안 쓴 것 (있으면 먼저 `/planning:spec`을 제안)
   - 남은 질문
   - 다음 세션의 첫 행동 한 줄

   `issue`: 이슈에 댓글 `### 진행 메모 YYYY-MM-DD`로 단다(`gh issue comment <N> --body-file -`). 지시서 자체(정할 것, 완료 기준 등)가 바뀌었으면 본문도 고친다(`gh issue edit <N> --body-file -`). `file`: 절의 "진행 메모"를 고친다.
3. **새 지시서 작성** — 항목마다:
   - 목표·산출물·완료 기준을 한 문장씩
   - 읽을 것: 이미 정해진 내용이 있는 **문서 절 번호**를 가리킨다. 대화 내용을 옮겨 적지 않는다
   - 정할 것: 열린 질문만. 정해진 것은 다시 묻지 않게
   - 조사할 것: 확인이 필요한 사실과 어디서 확인할지
   - 사용자 준비물(계정, 키, 설치, 결정)이 있으면 "선행 (사용자)"에 쓴다
   - `issue`: 이슈를 만들고 backlog.md "후보" 표의 이슈 칸에 `#N`을 적는다. `file`: `work-orders.md`에 절을 쓴다.
4. **권장 순서 갱신** (준비물이 필요한 항목은 뒤로): `issue`면 backlog.md 맨 위 "권장 순서" 표, `file`이면 `work-orders.md` 맨 위 표와 세션 체크리스트.
5. 사용자에게 지시서 요약(항목, 권장 순서, 사용자가 미리 할 일)을 보여 주고 확인받는다. 이슈를 만들거나 고치기 전에 이 확인을 받는다.
6. 로컬 파일이 바뀌었으면 `/planning:commit`으로 커밋한다. 열려 있는 기획 브랜치가 있으면 그 브랜치에, 없으면 기본 브랜치에 `docs: 작업지시서 갱신`(기본 브랜치면 확인 후). 이슈만 바뀌었으면 커밋할 것이 없다.

## 규칙
- 지시서는 대화 요약이 아니다. 다음 세션이 **무엇을 읽고, 무엇을 묻고, 무엇을 만들면 끝나는지**만 쓴다.
- 비밀값(키, 계좌번호)을 쓰지 않는다. "로컬 .env에 둔다"처럼 위치만 쓴다.
