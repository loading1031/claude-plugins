# 기획 문서 규칙

## 0. 프로젝트 설정 읽기

먼저 프로젝트 루트 `AGENTS.md`와 `CLAUDE.md` 및 그 파일이 가리키는 공통 규칙을 읽고 `## 기획 설정` 절을 찾는다. 같은 설정을 두 파일에 복사하지 않는다. 프로젝트의 명시적 예외와 현재 사용자 지시를 기본 절차보다 우선한다. 없으면 아래 기본값을 쓰고, 사용자에게 `/planning:init`을 안내한다.

**버전:** 플러그인에 버전 번호를 두지 않는다. 마켓플레이스 저장소의 커밋이 곧 버전이고, 프로젝트는 `.claude/settings.json`의 `extraKnownMarketplaces`에 `"autoUpdate": true`를 두어 늘 최신 커밋을 받는다(세션 시작 후 백그라운드로 받고, 다음 실행이나 `/reload-plugins`에 반영). 기획 설정에 최소 버전을 쓰지 않는다.

**CLAUDE.md에는 설정값만 둔다.** 진행 절차(명령 순서, 커밋·브랜치·이슈 규칙)는 이 플러그인의 스킬이 원본이다. 프로젝트 CLAUDE.md에 절차를 옮겨 적지 않는다(두 벌이 되면 어긋난다). 프로젝트 고유의 예외만 설정에 쓴다.

| 항목 | 기본값 | 뜻 |
|---|---|---|
| 기획 폴더 | `docs/planning` | 기획 문서가 있는 곳. 이하 `<폴더>` |
| 기준 문서 | `plan.md` | 전체 기획. 다른 주제 문서는 여기서 링크된다 |
| 시각화 문서 | 없음 | 다이어그램을 모아 둔 외부 문서(예: Claude Docs URL) |
| 용어 | 없음 | 프로젝트에서 정한 용어와 쓰지 않는 말 |
| 동기화 표 | 없음 | "무엇이 바뀌면 어디를 함께 고치나". 프로젝트 표가 있으면 아래 1.4의 기본 표보다 우선 |
| 기본 브랜치 | `main` | 기획이 끝나면 합쳐지는 브랜치 |
| 개발 브랜치 | 없음 | 있으면(예: `dev`) 코드 작업은 이 브랜치에서 분기한 작업 브랜치에서 하고 이 브랜치로 PR 한다. 기획은 그대로 기본 브랜치. 훅이 기본 브랜치에서 코드 브랜치 만들기, 기본·개발 브랜치에 바로 코드 커밋(`feat|fix|refactor|test`), 코드 PR의 base가 개발 브랜치가 아닌 것을 막는다 |
| 기획 브랜치 | `plan/<ID>-<slug>` | 백로그 항목 하나당 브랜치 하나. 예: `plan/B-03-frontend` |
| 합치기 방식 | 원격이 GitHub이면 `PR`, 없으면 `local` | `PR`: 머지 커밋 방식으로 PR을 합치고 PR 본문의 `Closes #N`으로 이슈를 닫음. `local`: `git merge --no-ff`. 둘 다 squash·rebase는 쓰지 않음 |
| 금지어 | 없음 | 기획 폴더에 쓰지 않을 말(쉼표로 구분). 훅이 커밋 때 검사한다. 인용(`"단계"`)은 허용 |
| 백로그 | `file` (단, `작업지시서: issue`와 `작업 추적`이 함께 있으면 `issue`) | `file`: backlog.md 색인. `issue`: GitHub 이슈가 작업 목록이자 지시서이며 별도 백로그 파일을 만들지 않음 |
| 작업 추적 | 없음 | GitHub 저장소 `OWNER/REPO`. 이슈 모드에서는 필수. 원격과 다르면 프로젝트 설정의 의도를 확인 |
| 작업지시서 | 원격이 GitHub이면 `issue`, 없으면 `file` | `issue`: 항목마다 GitHub 이슈 하나(본문 = 지시서, 댓글 = 진행 메모). `file`: `<폴더>/work-orders.md`. 1.6 참고 |

## 이슈 백로그 모드의 우선 절차

`백로그: issue`이거나, 백로그 설정 없이 `작업지시서: issue`와 `작업 추적: OWNER/REPO`가 함께 있으면 [GitHub 이슈 모드](references/issue-backlog.md)를 읽는다. 명시적 `백로그: file`은 기존 방식을 유지한다.

이슈 모드에서는 아래 기본 절차 중 backlog.md·work-orders.md·log.md를 만들거나 갱신하는 단계, B-ID와 plan 라벨 의무, 기획만 끝나면 이슈를 닫는 단계를 이 참조의 절차로 대체한다. `backlog`, `spec`, `commit`, `handoff`, `done`, `init` 모두 같은 모드와 저장소를 사용한다. 파일 모드에는 아래 절차를 그대로 적용한다.

## 1. 문서

### 1.1 구조

```
<폴더>/
├── <기준 문서>    전체 기획
├── <주제>.md      새 주제 기획 (기준 문서의 해당 절에서 링크)
├── backlog.md     다음 기획 후보
├── work-orders.md 작업지시서 (작업지시서 설정이 `file`일 때만. `issue`면 GitHub 이슈)
└── log.md         결정 이력 (최신이 위)
```

- 새 주제는 기준 문서의 한 절로 충분하면 거기에 쓴다. 한 화면을 넘으면 `<주제>.md`로 분리하고, 기준 문서에는 요약 3~5줄과 링크만 둔다.
- 파일명은 kebab-case 영어. 본문은 프로젝트 언어(설정이 없으면 사용자가 쓰는 언어).

### 1.2 새 주제 템플릿

```markdown
# <주제>

- 작성일: YYYY-MM-DD
- 상태: 초안 | 검토 중 | 확정
- 관계: <기준 문서> <절>의 상세. 관련 문서: <링크>

## 결론
한두 문장. 무엇을 하기로 했는가.

## 결정 사항
| 항목 | 결정 | 이유 |

## 상세
(표, 흐름, 다이어그램 우선)

## 데이터 모델 영향
없으면 "없음".

## 다른 문서에 반영할 곳
- <기준 문서> <절>: ...

## 확인이 필요한 것
- [ ] ...

## 출처
- [제목](URL)
```

### 1.3 작성 원칙

- 결론을 먼저 쓴다. 각 절의 첫 문장이 그 절의 답이다.
- 구조가 있는 내용(흐름, 상태, 비교)은 표나 다이어그램으로 쓴다. 문장으로 구조를 설명하지 않는다.
- **사실은 확인한 것만 쓴다.** 출처 페이지를 열어 확인한 것만 사실로 쓰고 URL을 남긴다. 블로그·2차 자료의 수치에는 "(2차 자료 기준)" 또는 "**검증하지 않음**"을 붙이고 확인 필요 항목에 넣는다.
- **사용자가 결정하지 않은 것은 "제안"으로 쓴다.** 결정으로 쓰지 않는다.
- 수치 파라미터는 한 표에 모으고 "가정값"임을 밝힌다.
- 프로젝트 설정의 "용어"를 지킨다. 쓰지 않기로 한 말을 쓰지 않는다.

### 1.4 동기화 (기본 표)

하나의 결정이 여러 곳에 반영된다. 한 곳만 고치지 않는다. 프로젝트 설정에 동기화 표가 있으면 그것을 따른다.

| 바뀐 것 | 함께 고칠 곳 |
|---|---|
| 기능·구조 | 기준 문서의 해당 절, 데이터 모델 절, 일정·마일스톤 절, 확인 필요 절 |
| 주제 문서 | 기준 문서의 요약과 링크 |
| 다이어그램이 있는 내용 | 문서 안의 텍스트 다이어그램(예: Mermaid) 먼저, 그다음 시각화 문서 |
| 용어 | 기준 문서의 용어 설명, CLAUDE.md |
| 프로젝트 수준 결정 | CLAUDE.md의 결정 사항 |

- 시각화 문서를 이번에 고치지 못하면 `backlog.md`의 "동기화 빚"에 적는다.
- 다이어그램을 고쳤으면 렌더링을 확인한다(가능한 도구가 있을 때).
- 문서끼리 수치·용어가 어긋나면 고치기 전에 사용자에게 알린다.
- 디스크의 파일이 마지막으로 읽은 내용과 다르면(사용자가 직접 편집했을 수 있음) 덮어쓰지 말고 차이를 먼저 보고한다.

## 1.5 브랜치

**백로그 항목 하나 = 브랜치 하나.** 기본 브랜치에서 갈라져 그 항목의 기획만 담고, 끝나면 기본 브랜치로 합친다.

```
main ──┬──────────────●── (merge) ──●──
       └ plan/B-03-frontend ●──●──┘
              pick       spec  commit   done
```

| 시점 | 하는 일 |
|---|---|
| `/planning:backlog pick <ID>` | 작업 트리가 깨끗한지 확인 → 기본 브랜치 최신에서 `plan/<ID>-<slug>` 생성·전환. backlog.md에서 항목을 "진행 중"으로 옮기고 브랜치 이름과 이슈 번호를 적는다(이슈 방식이면 이슈가 없을 때 만든다) |
| `/planning:spec` | 해당 항목의 브랜치 위에서만 문서를 고친다. 기본 브랜치에 있으면 멈추고 브랜치를 만들지 묻는다 |
| `/planning:commit` | 기획 브랜치에 커밋한다. 본문 끝에 `Refs: #<이슈>`(없으면 `Refs: <ID>`). 기본 브랜치에 `docs:` 커밋을 하려 하면 확인을 받는다 |
| `/planning:done` | backlog.md "완료"로 옮긴 뒤, 사용자 확인 후 기본 브랜치로 합친다(합치기 방식: PR 또는 로컬 `--no-ff`). 로컬 브랜치만 지운다 |

- slug는 주제를 2~3 단어 kebab-case 영어로.
- 브랜치를 오가기 전에는 커밋되지 않은 변경이 없어야 한다. 있으면 커밋할지, 어디에 둘지 묻는다. 임의로 stash하지 않는다.
- 여러 항목을 동시에 열면 `backlog.md`, `log.md`에서 충돌이 나기 쉽다. 두 파일의 충돌은 **양쪽 항목을 모두 살리는 방향**으로 푼다(log는 날짜순, backlog는 ID순).
- 기획 중 생긴 백로그 후보 추가는 그 항목 브랜치에서 함께 커밋한다.
- 원격(push)은 사용자가 요청할 때와 `/planning:done`의 PR 합치기를 사용자가 확인했을 때만.
- **원격 브랜치는 지우지 않는다.** 합친 뒤에는 로컬 브랜치만 지운다(`git branch -d`). 원격 브랜치는 사용자가 필요할 때 직접 지우므로 지울지 묻지도 않는다.
- **worktree:** 기본 브랜치가 다른 worktree에 체크아웃돼 있으면 이 폴더에서는 기본 브랜치로 전환할 수 없다. 새 브랜치는 `git fetch` 뒤 `git switch -c plan/<ID>-<slug> origin/<기본>`(원격이 없으면 `<기본>`)로 만들고, 로컬 합치기는 기본 브랜치가 열린 폴더에서 한다.
- **커밋과 이슈:** 커밋은 `Refs: #<이슈>`로 이슈를 가리키고, 이슈는 PR 본문의 `Closes #<이슈>`로만 닫는다.
- **기본 브랜치에 바로 커밋해도 되는 것:** 설정·도구 변경(`chore:`), 그리고 **결정을 더하거나 바꾸지 않는 작은 문서 수정**(`docs:` — 오타, 깨진 링크, 문구 다듬기, 이미 정한 내용의 위치 이동). 결정이 하나라도 들어가면 기획 브랜치에서 한다. 이 경우 log.md에는 쓰지 않는다.

### 1.5.0 PR 라벨

GitHub PR을 만들 때 변경 범위에 맞는 아래 라벨을 하나 이상 붙인다. 혼합 변경은 해당하는 라벨을 모두 붙인다.

| 라벨 | 적용 기준 | 색상 | 설명 |
|---|---|---|---|
| `plan` | 기획 문서·실행 계획만 변경 | `5319e7` | 기획과 계획 문서 |
| `design` | IA·화면 설명·와이어프레임·디자인 산출물 변경 | `a371f7` | 디자인 산출물 |
| `server` | 서버·API·데이터 계층 변경 | `1d76db` | 백엔드와 서버 변경 |
| `front` | 사용자 화면·프런트엔드 변경 | `0e8a16` | 프런트엔드 변경 |

PR을 만들기 전에 대상 저장소에 필요한 라벨이 있는지 확인한다. 빠진 라벨만 만든다. 기존 라벨의 색·설명은 자동으로 덮어쓰지 않는다.

```bash
gh label list --repo OWNER/REPO
gh label create plan --repo OWNER/REPO --color 5319e7 --description "기획과 계획 문서"
gh label create design --repo OWNER/REPO --color a371f7 --description "디자인 산출물"
gh label create server --repo OWNER/REPO --color 1d76db --description "백엔드와 서버 변경"
gh label create front --repo OWNER/REPO --color 0e8a16 --description "프런트엔드 변경"
```

라벨이 없으면 저장소의 라벨 관리자 권한으로 생성할 수 있는지 확인한다. 권한·네트워크 문제를 우회하지 말고 라벨을 적용하지 못했다는 점을 PR 작성자에게 알린다.

### 1.5.1 훅이 검사하는 것

플러그인 훅(`hooks/hooks.json`, Bash 실행 전)이 기획 설정이 있는 저장소에서 아래를 막는다. 막히면 규칙에 맞게 고쳐 다시 실행한다. 훅을 우회하지 않는다.

| 규칙 | 막는 것 |
|---|---|
| `git-add-all` | `git add -A`, `git add --all`, `git add .` |
| `commit-prefix` | 메시지 첫 줄에 접두어(`docs:` 등)가 없는 커밋 (`-m`·`-F`로 줄 때) |
| `commit-refs` | 기본 브랜치가 아닌 곳에서 `Refs:` 없는 커밋 |
| `code-branch-docs` | `plan/…`이 아닌 작업 브랜치에서 기획 폴더 커밋 |
| `banned-word` | 기획 폴더에 새로 쓴 줄의 금지어 |
| `pr-label-required` | GitHub PR 생성 명령에 `--label`이 없음 |

## 1.6 작업지시서

세션이 바뀌면 이전 대화가 없다. 다음 세션이 알아야 할 것은 대화가 아니라 작업지시서에 둔다. 둘 곳은 기획 설정 "작업지시서"가 정한다.

| | `issue` (원격이 GitHub일 때 기본) | `file` |
|---|---|---|
| 지시서 | 항목마다 이슈 하나. 제목 `<ID> <주제>`, 라벨 `plan`, 본문 = 아래 템플릿 | `work-orders.md`의 `## <ID> <주제>` 절 |
| 진행 메모 | 이슈 **댓글**로 날짜별로 쌓는다(`### 진행 메모 YYYY-MM-DD`). 본문은 지시서가 바뀔 때만 고친다 | 절 안의 "진행 메모" |
| 만드는 때 | `pick`할 때(없으면) 또는 `handoff`가 다음 후보 지시서를 쓸 때. `add`에서는 만들지 않는다(손에 잡을 일만 이슈로) | 같음 |
| 읽기 | `gh issue view <N> --comments` | 해당 절 |
| 끝낼 때 | PR 본문 `Closes #N`으로 닫힌다 | `done`이 절을 지운다 |
| 세션 체크리스트 | 프로젝트 `CLAUDE.md`의 기획 진행 방식 절 | 파일 맨 위 |
| 권장 순서 | `backlog.md` 맨 위 "권장 순서" 표 | 파일 맨 위 |
| 백로그와 연결 | backlog.md "후보"·"진행 중" 표의 이슈 칸에 `#N` | — |

템플릿:

```markdown
백로그 <ID>.

- 브랜치: plan/<ID>-<slug>
- 선행 (사용자): <준비물. 없으면 생략>
- 목표: 한 문장
- 산출물: <만들거나 고칠 문서와 절>

### 읽을 것
### 정해진 것 (다시 묻지 않는다)
### 정할 것 (사용자에게 물을 질문)
### 조사할 것 (출처를 열어 확인)
### 완료 기준
### 진행 메모
(`file`: 중간에 멈추면 결정된 것, 남은 질문, 다음에 할 첫 행동. `issue`: "댓글에 남긴다" 한 줄)
```

- `pick`할 때 지시서가 있으면 그것을 출발점으로 쓴다(진행 메모 포함).
- 지시서는 **이미 정해진 것을 다시 묻지 않도록** 쓴다. 정해진 것은 문서 절을 가리키고, 질문은 열린 것만 적는다.
- 이슈 본문의 문서 링크는 기본 브랜치 경로(`blob/<기본>/…`)로 쓴다. 아직 기본 브랜치에 없는 문서는 상대 경로 대신 파일 이름만 쓴다.
- 이슈 방식에서 라벨 `plan`이 없으면 처음 만들 때 함께 만든다(`gh label create plan`).
- 이슈를 만들거나 고치는 것은 외부(원격)에 쓰는 일이다. 저장소가 public이면 비밀값·개인 정보가 없는지 확인하고, 처음 만드는 이슈는 제목과 본문을 보여 주고 확인받는다.

## 2. backlog.md 형식

```markdown
# 기획 백로그

## 권장 순서 (작업지시서가 `issue`일 때)
| 순서 | ID | 이슈 | 사용자 준비물 |
|---|---|---|---|

## 후보
| ID | 주제 | 왜 필요한가 | 선행 | 우선순위 | 이슈 |
|---|---|---|---|---|---|
| B-01 | ... | ... | — | P0 | — |

## 진행 중
| ID | 주제 | 브랜치 | 이슈 | 시작 |
|---|---|---|---|---|

## 완료
| ID | 주제 | 결과 문서 | 날짜 |
|---|---|---|---|

## 동기화 빚
- [ ] ...
```

- ID는 `B-<번호>`. 번호는 재사용하지 않는다.
- 우선순위: P0 = 다음 마일스톤 착수 전에 필요, P1 = 해당 마일스톤 안에서 필요, P2 = 나중.
- "진행 중"은 1~2개를 넘기지 않는다.
- 이슈 칸은 작업지시서가 `issue`일 때만 쓴다. 이슈가 없으면 `—`. `file`이면 칸을 빼도 된다.
- **backlog.md는 색인이다.** "왜 필요한가"는 한두 문장(대략 150자 이내)으로 쓴다. 논의 경위, 사용자 결정, 후보 이름 같은 상세는 행에 쌓지 않는다:
  - 이슈가 있으면 이슈 본문("정해진 것")이나 댓글에, 없으면 log.md에 쓰고 행에는 "결정 있음(log YYYY-MM-DD)"처럼 가리키기만 한다.
  - 이미 긴 행은 `pick`할 때 상세를 이슈 본문으로 옮기고 행을 줄인다.

## 3. log.md 형식

최신 항목이 위에 온다. 결정만 기록한다(백로그 정리는 기록하지 않는다).

```markdown
## YYYY-MM-DD <유형> | <제목>
- 결정: ...
- 바뀐 문서: <파일> <절>
- 남은 것: B-12로 이관
```

유형: `decide`(결정), `update`(수정), `revert`(결정 번복), `sync`(동기화만).
