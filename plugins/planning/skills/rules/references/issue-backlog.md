# GitHub 이슈를 작업 목록으로 사용

## 설정과 범위

- `백로그: issue`, `작업 추적: OWNER/REPO`, `작업지시서: issue`를 사용한다. 기존 프로젝트의 `작업지시서: issue` + `작업 추적` 조합도 이 모드로 해석한다. 명시적 `백로그: file`은 기존 파일 방식을 유지한다.
- 프로젝트의 기본·개발 브랜치와 문서·Git 예외를 따른다. Codex 환경의 `codex/` 접두어도 허용한다. GitHub 기본 브랜치가 main이라고 가정하지 않는다.
- 작업 목록·목표·완료 기준은 이슈 본문, 진행 상태·검증·다음 행동은 댓글, 지속적인 요구사항·결정은 기존 주제 문서에 둔다. backlog.md, work-orders.md, log.md와 B-ID를 중복 생성하지 않는다.
- 모든 `gh` 조회·변경에 `--repo OWNER/REPO`를 명시한다. 인증·권한·네트워크 오류를 빈 목록으로 해석하지 않는다. Codex의 샌드박스에서 `error connecting to api.github.com`이 나면 실제 인터넷 장애로 단정하지 말고, 환경이 제공하는 네트워크 권한 요청/승격으로 같은 읽기 전용 조회를 재시도한다. 권한이 거절되거나 재시도도 실패하면 그 근거와 필요한 조치를 보고한다. 샌드박스 정책을 임의로 끄거나 자격증명을 출력하지 않는다. 저장소 설정이 없거나 상충하면 원격을 확인하고 필요한 값만 묻는다.
- 기존 이슈를 재사용한다. 라벨 `plan`을 강제하지 않는다. 기획 후보·구현 진행·운영 작업·과거 완료 기록을 구분하고, 제목만 보고 완료 여부나 우선순위를 단정하지 않는다.
- 이 스킬은 현재 세션에서 실행한다. 새 세션을 자동 생성하거나 다른 세션에 메시지를 보내지 않는다. 새 세션에서 같은 프로젝트의 backlog를 호출하면 저장소 이슈를 다시 읽는다. 이전 대화나 로컬 캐시를 기억한다고 가정하지 않는다.

## backlog

### 인자 없음

1. `gh issue list --repo OWNER/REPO --state open --limit 100 --json number,title,body,labels,assignees,url,updatedAt`로 열린 이슈를 읽는다. 100개 한도에 도달하면 페이지를 추가 조회하고, 일부만 읽었다면 범위를 밝힌다. 다른 사용자의 담당 작업도 표시하고 임의로 가져오지 않는다.
2. 현재 브랜치·연결된 PR·이슈 본문의 브랜치 링크를 대조해 진행 중 작업을 먼저 보여 준다. 제목의 `[진행]` 표시는 단서이며 실제 상태는 본문·댓글로 확인한다.
3. 추천 후보의 본문·댓글을 `gh issue view N --repo OWNER/REPO --comments`로 확인한다. 명시적 우선순위·선행 관계·준비물을 기준으로 다음 작업 하나를 추천한다. 우선순위가 없으면 추정임을 밝히고 임의로 라벨을 붙이지 않는다.
4. 번호·제목·현재 상태·다음 행동·링크를 간결히 보여 준다. 목록 조회만 요청받았다면 작업을 임의로 시작하지 않는다. 사용자가 이미 대상을 지정했다면 다시 선택을 요구하지 않고 pick으로 이어간다.

### pick <번호> 또는 pick #<번호>

1. 이슈 본문·댓글, 연결된 PR과 관련 문서를 읽고 목표·완료 기준·확정 사항·남은 일·다음 행동을 파악한다. 닫힌 이슈이면 종료 근거를 먼저 확인하고 임의로 재오픈하지 않는다.
2. 기존 원격/로컬 브랜치·worktree를 확인해 해당 작업을 재사용한다. 미커밋 변경과 stash를 임의로 옮기거나 지우지 않는다. 별도 checkout으로 안전하게 진행할 수 있으면 그렇게 하고, WIP가 꼭 필요하면 보존 위치를 확인한 뒤 복구 방법을 정한다. 브랜치 링크만으로 미커밋 WIP를 복구할 수 있다고 말하지 않는다.
3. 기존 브랜치가 없으면 프로젝트 통합 브랜치의 최신 원격에서 작업 성격에 맞는 브랜치를 만든다. 기획은 plan/<번호>-<slug>, 구현은 프로젝트의 feat/fix/chore 규칙을 따른다. 새 B-ID나 중복 이슈를 만들지 않는다.
4. 현재 요청이 허용한 범위에서 남은 작업을 시작한다. 이미 정해진 것은 다시 묻지 않는다. 미정인 제품 결정이나 필요한 준비물만 확인한다. 단순 기획 스킬 호출을 구현·배포·병합 전체의 허가로 확대하지 않는다.
5. 사용자가 이슈 해결을 요청했다면 완료 기준까지 계속 진행한다. 문서 하나 작성·커밋 하나 생성만으로 완료 처리하지 않는다. 구현이 필요한 이슈를 기획 문서 작성만으로 닫지 않는다. 중단이 필요하면 검증된 결과·남은 일·첫 다음 행동·브랜치/PR/커밋을 이슈에 남긴다.

### add <주제> / sweep

열린 이슈에서 중복을 확인한다. add는 목표·이유·완료 기준을 담은 이슈로 추가하고, sweep은 관련 문서의 미정 항목 중 사용자가 선택한 것만 추가한다. 이미 이슈 생성·수정을 승인한 요청이면 같은 승인을 반복해서 묻지 않는다. 기획 후보를 등록했다는 이유만으로 구현을 시작하지 않는다. 기존 후보를 갱신할 때 원래 본문·체크리스트를 보존한다.

## 다른 명령 연결

- **init:** 설정 위치(AGENTS.md 또는 CLAUDE.md)를 재사용하고 백로그 방식을 정한다. 이슈 모드에서는 작업 추적 저장소를 확인하고 파일 백로그·작업지시서·결정 로그 틀을 만들지 않는다. 기존 문서를 삭제하지 않는다. Claude marketplace 설정은 Claude 환경에서만 다루며 Codex에 같은 설치 동작을 가정하지 않는다.
- **spec:** 이슈에 연결된 현재 작업 브랜치에서 필요한 주제 문서와 직접 영향받는 문서만 갱신한다. 문서 수·기획/디자인/개발 삼중 구조를 강제하지 않는다. 동기화 빚과 남은 결정은 이슈에 기록한다. 기존에 승인한 결정 반영은 다시 승인받지 않는다. `check`는 불일치 보고이며 자동 수정하지 않는다.
- **commit:** 이슈 본문·댓글·연결 PR에서 번호를 확인해 `Refs: #N`을 사용한다. 기존 스테이징과 작업 외 변경은 보존한다. 프로젝트 커밋/검사 규칙을 따른다. 승인된 커밋·push 범위는 세션 내에서 재확인하지 않는다.
- **handoff:** 현재/지정 이슈에 변경·결정·검증·남은 일·다음 행동·실제 브랜치/PR/커밋을 댓글로 남긴다. 우선순위가 바뀌면 이슈의 선행 관계를 갱신한다. 별도 backlog 권장 순서표나 작업지시서 파일을 만들지 않는다. 새 세션은 pick으로 이 기록을 읽는다.
- **done:** 이슈의 전체 완료 기준과 검증 결과를 확인한다. 기획 이슈는 스펙 반영만으로 완료 처리하지 않는다. 실행 가능한 사용자 흐름이 있으면 기존 디자인·개발 이슈의 범위와 완료 기준을 확인해 연결하거나, 없으면 목표·범위·스펙 링크·선행 조건·완료 기준·검증 방법을 갖춘 후속 이슈를 만든다. 디자인은 별도 산출물이 필요한 흐름에만 만들고, 디자인이 구현을 막지 않으면 개발 이슈를 병행 착수할 수 있게 한다. 구현을 막지 않는 미정 사항은 제안/후속 범위로 넘긴다. 후속 이슈 번호와 의존 순서를 기획 이슈에 기록한 뒤에만 기획 이슈를 완료 처리한다. 이관하지 못한 구현이 남으면 진행 메모를 남기고 기획 이슈를 닫거나 PR에 `Closes`를 넣지 않는다. 전체 범위를 해결한 PR에만 `Closes #N`을 넣는다. 원격 PR 상태·checks·머지 대상·현재 head를 확인하고 기존 사용자 승인 범위에서 push·병합을 마친다. 승인이 없으면 검토 가능한 결과를 준비한 뒤 필요한 승인만 받는다. GitHub 기본 브랜치가 아닌 통합 브랜치에 합쳤다면 자동 종료를 가정하지 말고 실제 이슈 상태를 확인한다. 미완료 잔여 작업을 숨기려고 완료 기준을 축소하지 않는다. 원격 브랜치는 유지하고 로컬 정리는 프로젝트 규칙을 따른다.

## 예: 2nd-if

기존 `작업지시서: issue`, `작업 추적: loading1031/2nd-if`, `기본 브랜치: dev` 설정이면 별도 파일 없이 열린 이슈가 작업 목록이다. 이관된 진행/후속 후보도 라벨 없이 조회한다. 예를 들어 `backlog pick 17`은 #17 본문·댓글·관련 문서를 읽고, 로컬 WIP 보존 위치를 확인해 현재 세션에서 이어간다. 이슈 번호나 후보 목록을 플러그인에 고정하지 않는다.
