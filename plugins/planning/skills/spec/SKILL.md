# /planning:spec — 결정을 기획 문서에 반영

먼저 `rules` 스킬을 따른다(프로젝트 기획 설정, 템플릿, 작성 원칙, 동기화 표). 인자: `$ARGUMENTS`

먼저 `rules`에서 백로그 모드를 확인한다. **이슈 모드이면 [이슈 모드 참조](../rules/references/issue-backlog.md)의 이 명령 절차를 적용하고 아래 파일 모드 절차는 실행하지 않는다.** 프로젝트의 명시적 예외와 기존 사용자 승인 범위를 우선한다.

## <주제>

### 0. 브랜치 확인
현재 브랜치가 이 주제의 기획 브랜치(`backlog.md` "진행 중"의 브랜치)인지 확인한다. 기본 브랜치나 다른 항목의 브랜치에 있으면 멈추고, 전환하거나 `/planning:backlog pick`으로 브랜치를 만들지 묻는다.

### 1. 반영할 내용 확정
1. 이번 대화에서 **결정된 것 / 제안만 된 것 / 열린 질문**을 나눠 보여 준다.
2. 결정된 것만 "결정"으로 쓴다. 제안은 "제안"으로, 열린 질문은 확인 필요 항목으로.
3. **사용자 확인을 받은 뒤에** 쓴다.

### 2. 문서 작성
1. 기준 문서의 한 절로 충분한지, `<주제>.md`로 분리할지 정한다.
2. 분리하면 템플릿으로 새 문서를 만들고, 기준 문서에는 요약과 링크를 둔다.
3. 디스크의 파일이 마지막으로 읽은 내용과 다르면 덮어쓰지 말고 차이를 먼저 보고한다.

### 3. 동기화
동기화 표에 따라 함께 고칠 곳을 모두 고친다. 시각화 문서는 해당 도구로 고치고, 이번에 못 고친 곳은 `backlog.md` "동기화 빚"에 적는다.

### 4. 기록
1. `log.md` 맨 위에 항목을 추가한다(결정, 바뀐 문서, 남은 것).
2. `backlog.md`: 논의에서 새로 나온 주제를 "후보"에 추가한다. 항목을 "완료"로 옮기는 것은 `/planning:done`에서 한다.
3. 프로젝트 수준 결정이면 `CLAUDE.md`의 결정 사항을 갱신한다.

### 5. 커밋
`/planning:commit` 규칙으로 이 브랜치에 `docs:` 커밋을 만든다. 메시지에는 무엇을 결정했는지 쓴다.

### 6. 마무리 제안
1. 이 기획이 실행 가능한 범위까지 정리됐으면 스펙의 사용자 흐름·산출물별로 후속 작업을 나눈다. 별도 시각 설계가 필요한 흐름은 디자인 작업으로, 구현 가능한 결과는 개발 작업으로 연결한다. 디자인이 구현을 막지 않으면 개발을 디자인 완료까지 대기시키지 않는다.
2. 기존 작업이 있으면 issue 모드의 중복·범위 확인 규칙에 따라 재사용한다. 새 작업이 필요하면 목표·범위·스펙 링크·선행 조건·사용자 관점 완료 기준·검증 방법을 준비한다.
3. 구현을 막지 않는 미정 사항은 제안 또는 후속 구현 항목으로 남기고 기획을 진행한다. 이관이 필요한 후속 작업이나 구현을 막는 결정이 남아 있으면 `/planning:done`으로 기획 이슈를 닫지 말고 열린 일과 다음 행동을 기록한다.
4. 필요한 후속 작업이 연결되고 실행 순서가 정리됐으면 `/planning:done`을 제안한다.

## check
1. 기획 폴더 전체와 `CLAUDE.md`를 읽는다.
2. 아래를 찾아 보고한다. **고치지는 않는다.**
   - 같은 대상의 용어·수치·시간이 문서마다 다른 곳
   - 데이터 모델 절끼리, 또는 문서와 시각화 문서 사이의 차이(시각화 문서를 읽을 수 있을 때)
   - 텍스트 다이어그램과 본문 흐름의 차이
   - 프로젝트 용어에서 쓰지 않기로 한 말이 남은 곳
   - 확인 필요 항목 중 이미 확인된 것
3. 발견한 것을 `backlog.md` "동기화 빚"에 넣을지 묻는다.

## 규칙
- 한 번의 spec은 백로그 항목 하나를 닫는다. 여러 주제를 섞지 않는다.
- “기획 완료”는 문서 반영만 뜻하지 않는다. 실행 가능한 사용자 결과가 있으면 디자인 또는 개발 작업으로 이어지도록 이슈/백로그에 연결한다.
- 사실은 확인한 출처만. 확인 못 한 수치는 "검증하지 않음"과 함께 확인 필요 항목으로.
