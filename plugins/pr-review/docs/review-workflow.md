# PR 리뷰 워크플로

## 원칙

- 리뷰는 PR의 실제 변경이 일으키는 결함, 회귀, 요구사항 누락 또는 프로젝트 규칙 위반을 찾아낸다.
- 프로젝트의 `AGENTS.md`, `CLAUDE.md`, README, 디자인 기준과 관련 플러그인 원본 문서를 우선한다.
- 플러그인 규칙은 복사해 보관하지 않는다. `adapters/`가 가리키는 현재 문서를 직접 읽어 적용한다.
- 버그를 찾지 못했더라도 검토한 영역, 실행한 검사, 실행하지 않은 검증을 구분해 요약한다.

## PR 유형 분류

변경 파일과 PR 설명을 함께 읽고 다음 관점을 선택한다. 디렉터리명 하나만으로 리뷰 유형을 확정하지 않는다.

| 변경 영역 | 연결할 기준 | 검토할 내용 |
|---|---|---|
| Kotlin / Spring | `adapters/kopring.md` | 계층과 의존성 방향, 주입·영속성·트랜잭션·코루틴·외부 API·오류 처리 관례 |
| Next.js / TypeScript | `adapters/nextts.md` | App Router 경계, TypeScript 타입, 서버/클라이언트 분리, 컴포넌트·스타일·접근성 관례 |
| Django / 템플릿 | `adapters/django.md` | 서버·모델·폼·템플릿 관례, Tailwind/DaisyUI, 요청된 경우 HTMX/비동기 처리 |
| 디자인 문서 또는 화면 | `adapters/design.md` | 승인된 IA·와이어프레임·토큰·컴포넌트 기준, 화면 상태·흐름·접근성·반응형, 실물 코드와 문서 연결 |
| 계획·이슈·작업 문서 | `adapters/planning.md` | 저장소 계획 설정, 완료 기준·의존성·이슈 상태·문서 간 정합성 |

다른 스택이나 공통 저장소 변경은 해당 프로젝트의 기존 규칙과 변경 맥락을 기준으로 검토한다. 복수 영역 변경은 각각 검토하고 상호작용도 확인한다.

## 리뷰 작성

- 발견 항목마다 중요도, 문제 상황, 근거, 영향, 최소 수정 방향을 작성한다.
- 가능하면 문제를 일으키는 변경 라인에 인라인 의견을 연결한다. 같은 근본 원인의 여러 증거는 하나의 의견으로 묶는다.
- 변경되지 않은 줄 자체를 지적하지 않는다. 변경 줄에 직접 연결할 수 없는 전반적 우려는 심각도와 근거를 설명해 리뷰 요약에 둔다.
- 요청되지 않은 리팩터링이나 개인 선호는 지적하지 않는다.
- 디자인 변경은 승인 기준을 찾고 화면별 변경과 비교한다. 실제 렌더링·상호작용을 보지 못하면 소스만 확인한 범위를 명시한다.
- 테스트·빌드·브라우저 검증은 실제 실행한 경우에만 결과로 기록한다.
- 문제가 없으면 검토 범위와 검증 상태를 요약하고, 근거 없이 포괄적 승인 주장을 하지 않는다.

## GitHub에 리뷰 게시

현재 환경에서 GitHub 리뷰 기능을 사용할 수 있을 때만 제출한다. 권한이 없거나 PR을 식별할 수 없으면 사용자에게 파일·라인이 포함된 리뷰 초안을 제공한다. 리뷰 API가 지원하는 경우 인라인 의견을 작성하고 전체 판정은 발견 항목의 심각도에 맞춘다.
